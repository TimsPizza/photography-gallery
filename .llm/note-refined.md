# Photo Wall / Personal Photography Gallery — Early Dev Note

## Core Direction

This project is not just a photo management site. It should feel like an immersive photography space.

The goal is to let visitors enter without a clear purpose and still enjoy wandering through the photos. The default experience should be neat, smooth, fast-loading, and emotionally quiet. It should feel closer to walking through a visual archive than browsing a file list.

Core feeling:

- soft
- cinematic
- lightweight
- immersive
- personal
- mood-driven
- visually guided instead of navigation-heavy

This is a gallery/photo wall first, not a developer portfolio. No “contact me” section is needed because I already have a separate portfolio site.

## Visual Design

### General UI Style

The overall UI should use a soft liquid-glass style.

Main visual direction:

- liquid-glassified navbar
- background blur
- warm yellow / pale gray color palette
- light/dark mode support
- LXGW WenKai font
- subtle motion, not flashy dashboard animation
- soft shadows and translucent panels
- avoid hard, corporate SaaS feeling

The site should feel like a photography space, not a CMS admin panel.

### Navbar

The navbar should stay minimal and glass-like. It should support mode switching rather than traditional heavy navigation.

Potential top-level modes:

- Timeline
- Mood
- Tags
- Albums

The navigation should behave more like browsing semantics than page routing.

## Page Structure

### Single-page Direction

A single-page design is preferred because it preserves immersion. Frequent route changes can break the feeling of staying inside one visual space.

Default idea:

- main page is a vertically scrolling photo wall
- clicking a photo opens a modal / overlay
- modal keeps the user inside the same visual environment
- albums may use a separate immersive layout if needed

A single-page layout with modal interaction is harder to design, but it fits the project better than a traditional multi-page gallery.

### Layout System

Use a 12-column grid layout.

Reasons:

- works well with 3:2 and 2:3 photography
- easy to map landscape and portrait photos into different spans
- mobile-friendly
- works well with auto-layout logic
- flexible enough for album layouts later

The layout should not be a dumb masonry wall only. It should be aware of photo orientation, aspect ratio, and grouping context.

Need a layout calculator tied to the layout component.

Inputs:

- photo width / height
- aspect ratio
- orientation
- group context
- maybe importance / featured flag later

Possible layouts:

- timeline wall layout
- mood cluster layout
- album showcase layout

## Default Browsing Mode: Timeline

By default, photos should be sorted and vertically stacked by capture time, not upload time.

This creates a natural visual timeline of my photography.

Primary source:

- EXIF `DateTimeOriginal`

Fallback order:

1. EXIF `DateTimeOriginal`
2. EXIF `CreateDate`
3. file modified time
4. upload time

Add a timeline indicator as the temporal spine of the gallery.

Timeline indicator ideas:

- subtle vertical line on the side
- sticky year/month marker
- active section highlight
- soft dots for clusters, not every single photo
- current visible time range shown while scrolling

Example display:

- `May 2026`
- `2026 · Spring`
- `May 31 · Rain / Campus / Birds`

Timeline groups can be generated by:

- day
- month
- shooting session
- album/event

Grouping density should depend on the number of photos.

Small library:

- group by day

Medium library:

- group by month with day sublabels

Large library:

- group by month, active photo shows exact day

Important: GPS EXIF should not be shown directly. If location is used, it should be coarse, such as city/region/category, not exact coordinates.

## Mood Mode

Mood Mode should not feel like a normal filter button.

It should be a scene transition.

When the user clicks the Mood button, the page should feel like a cinema preparing to start:

- lights dim
- background darkens
- timeline fades back
- gallery recedes
- mood/color clusters slowly float up

Design principle:

Mood Mode should feel like the lights dimming before a film starts.

Interaction sequence:

1. User clicks Mood Mode.
2. Ambient light dims.
3. Timeline indicator fades out or becomes secondary.
4. Chronological layout softens / recedes.
5. Mood clusters emerge.
6. User browses by visual feeling instead of time.

Mood Mode = lights down, time steps back, emotions come forward.

Possible mood cluster labels:

- Warm Film
- Rain Gray
- Fresh Cyan
- Deep Green
- Golden Autumn
- Teal Orange
- Black & White
- Low-key Shadow
- Soft White
- Blue Hour

Each cluster can appear as a floating card / color island / stack.

Each mood cluster should show:

- representative color gradient
- 3–6 preview thumbnails
- mood name
- photo count

The user should feel like choosing a visual atmosphere, not applying a spreadsheet filter.

## Color / Mood Classification

### Main Idea

Mood categories should not be hard-coded color buckets only.

The system should use each photo’s color fingerprint, then build mood groups from the growing distribution of all uploaded photos.

In simple terms:

- each photo gets stable color metadata
- global mood groups can be rebuilt as the library grows
- early categories stay broad
- later categories can become more refined

Broad first, fine later.

### Photo Color Fingerprint

On upload, each photo should be analyzed into a color fingerprint.

Stored information:

- dominant colors
- percentage of each dominant color
- average color
- brightness
- saturation
- contrast
- warmth/coolness
- possibly vibrant/muted/dark/light palette values

Do not rely only on average color. Average color is useful for ambience but bad for classification because mixed-color photos can collapse into muddy neutral colors.

A better fingerprint should include dominant color distribution.

Example structure:

```ts
type PhotoColorFingerprint = {
  dominantColors: {
    color: string;
    percentage: number;
    role: "dominant" | "secondary" | "accent";
  }[];
  averageColor: string;
  brightness: number;
  saturation: number;
  contrast: number;
  warmth: number;
  palette?: {
    vibrant?: string;
    muted?: string;
    darkVibrant?: string;
    lightVibrant?: string;
    darkMuted?: string;
    lightMuted?: string;
  };
};
```

### Existing Libraries

Do not build the color extraction engine from scratch in the first version.

Candidate libraries:

- `node-vibrant` / Vibrant.js for palette extraction
- `Color Thief` for dominant color / palette extraction
- `fast-average-color` for lightweight average/background color
- `sharp.stats()` if backend image processing is needed
- `Color.js` later for perceptual color distance / Delta E

First version should probably use `node-vibrant` or `Color Thief`, then store the result.

### Adaptive Mood Buckets

The long-term idea is an adaptive bucket system.

Initial rough buckets could be simple:

- Red
- Green
- Blue
- Yellow
- Gray
- Monochrome
- Warm
- Cool
- Dark
- Light

As the sample size grows, broad buckets may split into more specific mood buckets:

- Red → light red / muted red / warm pink
- Green → fresh green / moody green / deep forest
- Blue → cyan blue / dark blue / gray blue
- Yellow → warm film / golden autumn / pale sunlight

However, splitting should not be based only on bucket size.

A bucket should split only when:

- it has enough photos
- internal variance is high
- proposed child groups are visually distinct
- child groups are far enough apart in perceptual color space
- both children have enough photos
- the split is useful for UI, not just mathematically possible

Important principle:

UI usefulness beats mathematical purity.

If two subgroups are technically different but visually almost the same, do not split them. This is a photography browsing feature, not a color science benchmark.

The algorithm should suggest splits, not permanently enforce them.

Example:

```txt
Suggested split:
Blue → Fresh Cyan + Dark Blue

Fresh Cyan:
42 photos
bright cyan, muted green, high brightness

Dark Blue:
19 photos
low brightness, deep blue, high contrast
```

Then I can accept, rename, merge, split, or ignore.

The photographer keeps final control.

## Upload / Processing Pipeline

Heavy work should happen at upload time, not at request time.

Do not calculate colors or clustering on every page request.

Preferred pipeline:

```txt
Client upload page
  ↓
select photos
  ↓
client reads EXIF
  ↓
client resizes image to small analysis size
  ↓
client extracts palette / fingerprint
  ↓
client generates preview metadata
  ↓
client uploads image + metadata
  ↓
server stores metadata in database
  ↓
frontend only reads precomputed data
```

Client-side processing makes sense because the user’s machine usually has more compute headroom than a serverless function.

Use browser APIs:

- `createImageBitmap`
- Canvas / OffscreenCanvas
- Web Worker
- EXIF parser such as `exifr`
- palette extraction library if browser-compatible

Important:

- do not analyze full-resolution images
- resize to around 128–256px for color extraction
- process uploads with limited concurrency
- use Web Worker if batch uploading many photos
- store algorithm version with fingerprint

Example metadata fields:

```ts
type PhotoMetadata = {
  id: string;
  fileName: string;
  captureTime: string;
  uploadTime: string;
  width: number;
  height: number;
  aspectRatio: number;
  orientation: "landscape" | "portrait" | "square";
  camera?: string;
  lens?: string;
  iso?: number;
  aperture?: string;
  shutter?: string;
  focalLength?: string;
  colorFingerprintVersion: number;
  colorFingerprint: PhotoColorFingerprint;
  manualTags: string[];
  autoMoodTags: string[];
};
```

The server should not fully trust client metadata forever. It should store the fingerprint version so metadata can be rebuilt later if the algorithm changes.

## Mood Group Rebuild

Mood groups should not be recalculated on every request.

Possible rebuild triggers:

- manual admin button: “Rebuild Mood Groups”
- after every N new photos
- scheduled job later, only if needed

First version can use manual rebuild only.

Rebuild process:

```txt
read all photo fingerprints
  ↓
run grouping / clustering logic
  ↓
generate mood clusters
  ↓
assign photos to clusters
  ↓
store cluster version
  ↓
frontend reads latest stable version
```

The frontend should only read precomputed mood clusters.

Albums need a different layout for immersive showcase.

Album features:

- manual layout override
- album-specific visual rhythm

Possible album layout types:

## Performance Principles

The site must feel fast.

Rules:

- never process images during normal page requests
- never cluster during normal user browsing
- use precomputed metadata
- use responsive images
- lazy-load below-the-fold photos
- use thumbnails first, larger versions on modal/open
- keep animation smooth and restrained
- avoid overloading the page with huge JS libraries

The expensive parts should happen during upload or admin rebuild, not during visitor browsing.

---

## Motion / Interaction

Use motion to support immersion, not to show off.

Possible libraries:

- Framer Motion for layout transitions
- Lenis or another lightweight smooth-scroll library
- React Bits may still be useful for selected effects

Motion ideas:

- soft modal expansion
- timeline indicator fades between sections
- mood mode lights-down transition
- color clusters float upward
- album pages transition like visual chapters

Avoid:

- over-animated UI
- dashboard-like transitions
- random parallax everywhere
- motion that fights the photos

Photos should remain the center.
